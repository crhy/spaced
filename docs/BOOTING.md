# Spaced Linux boot process

This document describes the Spaced Linux live boot path, how it differs from a
stock Devuan live system, every historical boot failure that has shipped, and
the guards that keep those failures from coming back.

## Boot chain

```
Firmware (BIOS/UEFI)
  -> GRUB (live-build grub-pc / grub-efi, live GRUB menu)
  -> Linux kernel (live-boot initramfs)
  -> live-boot mounts /run/live/medium, unsquashfs the live filesystem
  -> plymouth splash (default entry only)
  -> sysvinit /etc/rcS.d + /etc/rc.d rc scripts
  -> LightDM autologin as "user"
  -> MATE session, Compiz window manager
```

## Live GRUB menu

The live GRUB menu is authored in
`live-build/config/bootloaders/grub-pc/grub.cfg` and rendered by live-build's
`grub-pc` bootloader stage. The menu is **not** generated by `update-grub`; it
is hand-written and must be kept consistent with `live-build/auto/config`'s
`--bootappend-live`.

| Entry | Command line | Purpose |
|---|---|---|
| Start Spaced Linux | `@APPEND_LIVE@` (`boot=live components quiet splash username=user hostname=spaced`) | Default hardware-agnostic boot |
| safe graphics | `boot=live components nosplash nomodeset` + nouveau/`nvidia-drm.modeset=0` | Drives that hang on kernel modeset; text console |
| verbose boot | `boot=live components noplymouth console=tty0 noquiet loglevel=7` | Full serial-to-VGA boot log for diagnosis |
| Verify the boot medium | `@APPEND_VERIFY_CHECKSUMS@` | `live-boot` medium integrity check |

`--bootappend-live` lives in `live-build/auto/config` and supplies the default
entry. `@KERNEL_LIVE@` / `@INITRD_LIVE@` / `@APPEND_LIVE@` /
`@APPEND_VERIFY_CHECKSUMS@` are substituted by live-build.

## Comparison to a stock Devuan live boot

Stock Devuan (and Debian live-build) ships roughly the same skeleton:

- `boot=live components quiet splash`
- Same GRUB theme mechanism (`/boot/grub/config.cfg`, `grub.cfg` menuentries)
- Same `live-boot`/`live-config` userspace, with `live-config-sysvinit` for the
  init selection
- plymouth for the splash on the default entry

The historical Spaced differences that caused hardware failures were **not**
present in stock Devuan:

1. A QEMU-only display name in the kernel command line
2. A forced early GPU modeset
3. A forced serial console

All three are now forbidden (see "Hardening" below). Other intentional
differences (autologin LightDM, `nouveau.modeset=0`/blacklist in the safe
entry) are desktop policy, not boot-breaking.

## Boot failure history and resolution

### 8.26.0 — `video=Virtual-1:1280x1024` (QEMU display name on hardware)

**Symptom:** Live USB boots to GRUB, chooses the default entry, then sits on a
blinking cursor or a blank screen; no framebuffer is set up.

**Cause:** The default GRUB entry appended
`video=Virtual-1:1280x1024`. `Virtual-1` is the output name that
QEMU/KVM's virtual GPU exposes; a physical machine has no such output, so the
kernel could not set a video mode and left the console blank.

**Resolution:** Removed from the live GRUB entry (commit `c43be09` had removed
it from the *installed* system's `/etc/default/grub`, but the live menu, which
is what a user actually boots, still carried it). The current menu has no
`video=` argument at all; GRUB's `gfxmode`/`gfxpayload` handling and the
kernel's native framebuffer detection take over.

### 8.26.0 — `console=ttyS0` (serial console on hardware without a serial port)

**Symptom:** Default live boot leaves a blinking cursor in the top-left; later
sysvinit logs show `INIT: Id "S0" respawning too fast`.

**Cause:** `console=ttyS0` forced the kernel console onto a serial port that
most machines do not have, so console output went nowhere, and the chroot hook
unconditionally added an `S0` getty to `/etc/inittab`.

**Resolution:** Removed `console=ttyS0` from `--bootappend-live` and stopped
adding the `S0` getty (commit `e1a2476`). The verbose boot entry now uses
`console=tty0` explicitly so the console always has a visible target.

### 8.26.0 — `nouveau.modeset=1` forced at boot

**Symptom:** On NVIDIA hardware, early forced nouveau modesetting can hang or
black-screen during boot before the desktop can load.

**Cause:** `--bootappend-live "… nouveau.modeset=1 …"` forced the nouveau DRM
driver to modeset at kernel init on every machine. Stock Devuan does not do
this; the Xorg `xserver-xorg-video-nouveau` driver handles display at session
start.

**Resolution:** Removed from the default boot append line. The live system
still carries the nouveau X driver and NVIDIA firmware for installed use; only
the early kernel-time force is gone. The safe graphics entry explicitly sets
`nouveau.modeset=0` for hardware that needs it.

## Hardening (how these cannot come back)

`scripts/check.sh` now fails the build if any of the following regress in
`live-build/auto/config` or the live GRUB menu:

- `video=` or `Virtual-1` anywhere in the live GRUB config
- `console=ttyS0` or `ttyS0` in the live kernel command line
- `nouveau.modeset=1` in the default boot path
- The `boot=live components quiet splash` default append line changing shape
- A `virtio-gpu-pci` / `virtio-vga` test-VM GPU (must stay a single `-vga std`)

`make check` runs this gate before any ISO is produced. If you are changing
boot configuration, run:

```bash
make check
```

and, after building, `make iso-test` (QEMU) plus a real USB boot before
release.

## The test-VM black screen on this project

If `make iso-test` shows a black screen with a blinking cursor even though the
real hardware boots, check the QEMU video device, not the ISO. Earlier test
scripts layered a `virtio-gpu-pci` (or `virtio-vga`) device on top of QEMU's
default VGA, so the guest saw **two DRM cards**; the guest's Xorg stalled
during screen setup and LightDM never brought up the greeter or an autologin
session. The live kernel itself had booted fine (SSH up, `/run/live/medium`
mounted) — only the display stopped.

The fix is to expose exactly one stable card (`-vga std`). The guards in
`scripts/check.sh` reject a second virtio GPU.

## Troubleshooting a failed boot

Use the **verbose boot** GRUB entry (`noplymouth console=tty0 noquiet
loglevel=7`) to capture the full boot log instead of a splash.

Common live-boot errors and their meaning:

- `usb 3-4: device descriptor read/64, error -110` — a USB device timed out
  during enumeration. This is frequently harmless (a hub or device on the same
  port tree). It is **not** the cause of a hang unless it repeats and the boot
  stops at that line; a bad USB stick or port can do that, in which case try a
  different port or rewrite the stick.
- Stop at `Begin: Waiting for root file system …` — the medium was not found.
  Check the stick/port, or use the Verify entry.
- Blinking cursor with no log lines — historically the QEMU `video=Virtual-1`
  or `console=ttyS0` regressions above; the guards prevent them from shipping
  again.
