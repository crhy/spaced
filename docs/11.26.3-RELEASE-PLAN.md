### Actual reboot acceptance gate — 2026-11-20

Restart must restart the kernel, not merely end the desktop session. A greeter
return with an unchanged `/proc/sys/kernel/random/boot_id` is a failed reboot.
Neither a successful D-Bus reply, SSH reconnect, nor session disappearance is
proof. Retain valid before/after boot IDs, relevant logs, and candidate identity.

Local test hardening: `scripts/vm/qemu/reboot-loop.sh` now rejects missing or
malformed boot IDs, requires distinct IDs, and fails missing-user-session or
denied-user-request cases instead of passing via a privileged fallback. Focused
tests simulate a return to the greeter on the same boot and missing boot IDs.
This is test hardening, not evidence that the underlying runtime fault is fixed.
The SSH/su D-Bus probe is not equivalent to clicking the actual MATE menu.

Desktop test mode is now available with `SPACED_REBOOT_TRIGGER=desktop`.
It activates the actual English MATE shutdown dialog as the live user, disables
the dialog countdown, waits for MATE's Running phase, and never retries power
requests as root. SSH availability alone was insufficient: the first automated
attempt exposed a startup race, which is recorded as a failed test, not an OS
reboot failure. Two manual Restart activations on the released 11.26.2 BIOS
live ISO produced changed kernel boot IDs; actual GUI shutdown exited QEMU.
This is baseline evidence only, not an installed/upgrade/candidate acceptance.

The corrected automated BIOS/live baseline passed two Restart rounds and one

### RAM temperature (requested addition)

- Discover supported system-memory temperature sensors through the kernel's exposed sensor interfaces. First verify which readings the workstation actually exposes; do not promise a temperature for hardware without an accessible sensor.
- Show RAM temperature in the memory view, with per-module readings when reliably identifiable. If an overview uses the hottest module, label it explicitly. Do not confuse GPU VRAM, CPU or motherboard temperatures with RAM temperature, and do not invent DIMM-slot mappings.
- Show `Unavailable` when readings are absent, inaccessible or stale; never substitute zero or an estimated temperature. Keep collection read-only, lightweight and unprivileged during normal use. Do not probe/write SMBus devices or change firmware settings automatically.
- Test absent sensors, one/multiple modules, ambiguous labels, permission errors, invalid readings and disappearing sensors. Validate real readings against the corresponding exposed sensor values when available, and verify the unavailable state otherwise.

### Hardware tab cleanup (requested addition)

Proposed design: compact device summaries with expandable detail, rather than equally sized cards dominated by gauges or long raw sensor lists. Keep Overview as the graphical dashboard and Hardware as the readable inventory/live-stat view.

- CPU and Memory summaries first, followed by one compact row per GPU, then Storage, Network and Other Sensors sections. Put relevant temperatures beside their devices; preserve unmatched readings under Other Sensors without guessing their identity.
- Keep model, utilization, temperature and memory/power where applicable visible without expansion. Move per-thread meters, DIMM details, driver/PCI information, mount lists and interface addresses into expandable sections. Remember expansion state.
- Remove duplicated large gauges and unnecessary blank space, not legibility. Align values and units; reflow at narrow widths without clipped values. Use consistent text sizes, keyboard-operable expanders, theme-following colours and non-colour status labels.
- Reuse row widgets on refresh, retain scroll/focus/expansion state and device ordering, and ensure disappearing/reappearing sensors do not accumulate hidden rows. Correct CPU-meter tooltips for cores beyond the first row and distinguish logical threads from physical cores.
- Test default, narrow and large-text layouts with multiple GPUs and many sensors; review rendered screenshots before settling the layout. Keep the compact/focus improvements from 0.1.9 where applicable.

### Full-window device details (requested addition)

- Double-click any Overview or Hardware card/device summary to open a full-window detail view for that specific card. This extends the existing focus behavior: reveal related details rather than merely scaling up the summary. Each GPU opens its own device view, not the first GPU or an aggregate.
- CPU details include available model/topology information, physical cores versus logical threads, total/per-thread utilization, frequencies, CPU temperatures, power and bounded recent history. Clearly distinguish measured, advertised and unavailable values; do not invent unsupported readings.
- Memory details include usage breakdown, available/cache/swap, identifiable module information and RAM temperatures. GPU details include utilization, VRAM, temperatures, power, driver/PCI information and supported device-specific readings. Storage, Network and sensor cards likewise expose their related devices/readings and available history, without unrelated dashboard content.
- Provide a visible Back control and Escape to return to the previous tab, scroll position and expansion state. Retain double-click-to-restore on non-interactive detail-card surfaces; clicks on buttons, expanders, text selection or other controls must not trigger navigation accidentally. Provide a keyboard-accessible Details action as an alternative to double-click.
- Keep live updates and theme following active in detail views. Reuse existing collectors and bounded histories rather than launching duplicate sampling workers. Handle a device disappearing with an unavailable state and a working Back control; never silently switch identities.
- Test entry/exit for every card type and each GPU, keyboard access, child-control interactions, narrow/large-text layouts, theme changes, device loss and repeated navigation without leaked widgets, timers or workers.

Additional feature dispositions:

- Approved and implemented: a single Celsius/Fahrenheit preference applied consistently to all temperature displays (Fahrenheit default), plus current/session-maximum readings and a reset action in expanded details.
